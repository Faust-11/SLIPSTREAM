## 2026-11-11 · Маршрутизація мов і 404 (Task 3, після рев'ю)
**Заміри.**
1. `notFound()`, викликаний зі сторінки, у Next 16.1.7 / 16.2.12 / 16.4.5 / 16.4.6 віддає сервером порожній документ `<html id="__next_error__">` (без `lang`, макета й тексту); 404 малює лише клієнт. Відкритий баг vercel/next.js#62228 (з 2024; дублікати #99287, #99793, #100596; незлиті PR #98583, #100648). Unmatched URL рендеряться сервером, але без `experimental.globalNotFound` — стандартною англійською заглушкою поза `[lang]/layout`.
2. **500** на `/teams.rsc`, `/uk.rsc` (`InvariantError: Expected RSC response, got text/html … This is a bug in Next.js`, схоже — vercel/next.js#101449, закрито без виправлення) виникає лише за **поєднання proxy + динамічного `global-not-found`** (читав `headers()`); кожне окремо — 404 (замір рев'юера, варіанти B/C/D). **Правило:** коли proxy повернеться (фаза 7), `global-not-found` лишати статичним; e2e-перевірка `/teams.rsc` ловить цю регресію.
3. Proxy в Next 16 працює на Node runtime (`proxy.md`) і викликається на кожен запит сторінки.

**Рішення.**
- Мови — правилами `redirects` (`/en`, `/en/:path*` → 308 без префікса) і `rewrites.afterFiles` (решта, крім `/uk…`, `/en…`, `_next/`, → `/en/…`) у `next.config.ts`. За `rewrites.md` `afterFiles` виконуються після файлів, але до динамічних маршрутів. `src/proxy.ts` немає; з'явиться лише для логіки на запит (фаза 7, вузький matcher).
- `src/app/global-not-found.tsx` — **статичний** і двомовний: без JS видно обидві секції з власним `lang`; inline-скрипт до першого кадру ставить `html[lang]` за адресою (`/uk…` → `uk`) і ховає іншу секцію. Заголовок вкладки нейтральний — «404 · Slipstream»: React під час гідратації повертає текст `<title>`, тож мовний заголовок скриптом не втримати (перевірено трасуванням).
- Неіснуючі параметри закривати через `dynamicParams = false` + `generateStaticParams` (unmatched → серверний 404). Явний `notFound()` — лише коли інакше не можна; для нього `src/app/[lang]/not-found.tsx` (мова після гідратації через `next/root-params`).
- Catch-all `[...rest]` не використовуємо: він перетворює unmatched URL на `notFound()` і повертає баг 1.
- e2e перевіряє сирий серверний HTML 404, RSC-запити (404, не 500) і редирект `/en//evil.com` (лише свій домен) — проганяти й проти прев'ю Vercel (Task 8), бо нормалізацію `//` там не перевірено.
- `/_global-error` (службова сторінка Next, за прямою адресою відповідала 500 з кешем на рік) → `beforeFiles` rewrite на `/_not-found` (404); справжні помилки й далі 500.
- Регістр: редиректи `/EN…` нечутливі до регістру (308), `/UK…` → 404 — безпечно, лишаємо.
- Латентний ризик (Task 6): мова 404 живе в атрибутах `<html>`, які ставить скрипт; помилка гідратації client-компонента в 404 перемалює корінь і скине вибір (замір рев'юера з навмисним mismatch). Перевірити обгортку `<Suspense>` замірами, коли в 404 з'являться шапка/футер; `expectBrowser404` таку регресію ловить.
- `public/e2e-probe.txt` — перевірка, що rewrite не ламає `public/`; замінити на реальний файл, коли з'являться фото (фаза 3).

  проєкту; знайдено `/code-review high` — перша версія правки знімала такій сесії cookie, і вхід «вдавався», але миттєво скидався, а одноразовий код згорав)
  — «недоступно», **cookie не знімаємо і refresh не ротуємо** (новий токен був би таким самим). Підробка зі схожою структурою (issuer публічний) обмежена
  **30 оновленнями / 10 хв на джерело**, далі — «недоступно», сесію не знімаємо. Прострочення свідомо не вимагаємо: після ротації ключів проєкту справжній
  токен із майбутнім `exp` не пройде підпис, і саме refresh видасть новий.
- **Причини помилок** — `gotrue.ts`: «не схоже на адресу» лише за `email_address_invalid` (чи `validation_failed` про пошту), «невірний код» лише за
  `otp_expired`/`otp_invalid`, ліміти `over_*_rate_limit` → 429; решта 4xx (`signup_disabled`, `email_provider_disabled`, `email_address_not_authorized`, …)
  — «недоступно». `rest.ts`: 403 PostgREST (42501 — немає grant/Exposed schema) — «недоступно», а не «сесія завершилась» (було: петля «увійти знову → 403»).
- **Профіль `profile:false`** — `ProfilePanel` показує «недоступно» й «Вийти», а не форму вибору ніка (upsert перезаписав би наявний нік).
- **Доступність** — «Скасувати» у режимі зміни ніка; «Нікнейм збережено.» у живому регіоні, що завжди є в DOM; фокус повертається на «Змінити
  нікнейм»; після відповіді на «Надіслати новий код» (і після помилки запиту) фокус іде в поле кроку. До гідратації `/profile` показує «Завантаження…»,
  а «Ви не ввійшли» лишається в `<noscript>` (серверний знімок — завжди «аноним»; для того, хто ввійшов, цей блок мигав). Ціна: аноніму на мить
  видно «Завантаження…» замість блоку входу.
- **Міграція 0016 ідемпотентна** — відтворено в CI (Postgres 17): `DuplicateColumn: column "nick_key" of relation "profiles" already exists`. Тепер
  `drop constraint if exists` + `add constraint`, `add column if not exists`, `create unique index if not exists`; `db.yml` виконує файл удруге й перевіряє
  наявність індексу, колонки й constraint.
- **Додатково за `/code-review high` по підсумковому diff (20.11):** (а) HS256 — див. вище (регресія першої версії правки refresh: наш токен з alg поза
  ES256/RS256 тепер «недоступно» без зняття cookie й без refresh); (б) `/api/session` знімає позначку `outlap_in`, коли сесії немає й це не збій (раніше до
  30 діб кожна сторінка робила зайвий запит); (в) після `verify` форма входу перевіряє стан акаунта (`getAccount`) — cookie не збережено/сесія недоступна →
  «недоступно» замість форми ніка (нік-POST дав би 401, а одноразовий код уже згорів); (г) `account-store` нумерує запити: застаріла відповідь
  `/api/session` не перезаписує `setAnonymous`/`setNick`; (д) `readJson` міряє ліміт тіла в **байтах** UTF-8, а не в одиницях UTF-16 (кирилиця).
- **Не виправляємо (прийнято):** життя access JWT після logout/delete (до 1 год; перевірка локальна за JWKS); `readJson` без `Content-Length` читає тіло
  до перевірки розміру (спасає ліміт Vercel 4,5 МБ); довіра до `x-forwarded-for`/`x-real-ip` (на Vercel платформа їх перезаписує; на іншому хостингу
  ліміти підроблювані); **`delete` по вкраденому access:** акаунт можна видалити, маючи лише чинний access-токен (до 1 год), без повторної
  автентифікації — відкладено; «паритет JS↔SQL» перевіряє `db.yml` (JS-бік у vitest звіряється з фікстурою, згенерованою з тих самих правил).

### Фаза 9a — нік: allowlist + NFKC + унікальність за «скелетом» (рішення координатора 20.11, security-ревью `validate.ts`)
Чорний список невидимих символів (мій попередній `HIDDEN_OR_ODD`) — неповний; нік публічний (таблиця, чемпіони), тож підміна чужого
ніка невидимими/схожими символами неприпустима. Замінено на **allowlist + нормалізацію + скелет** з однаковими правилами в JS і SQL.
- **Єдине джерело правил — `src/lib/play/nick-rules.mjs`** (без залежностей; його читають і сайт, і фейк Supabase, і генератор фікстури).
  1. **NFKC перед перевіркою** (повна ширина, nbsp/ідеографічний пробіл → звичайний, лігатури). 2. **Allowlist:** A–Z, 0–9, кирилиця
  **лише U+0400–U+045F та Ґ/ґ (U+0490/0491)** — повні пари, які згортає таблиця (друге security-ревью 20.11: діапазон U+0400–U+04FF мав Ӏ U+04C0 та ін. двійники латиниці), роздільники `. _ -` і ОДИН пробіл між словами; перший/останній
  символ — літера чи цифра; без подвійних пробілів; довжина 3–24 символи (code points; комбівних немає — це й графеми). 3. **Скелет
  для унікальності:** NFKC → мала кирилиця (явна таблиця U+0400–042F, Ґ) → мала ASCII → схожі кириличні літери → латинські
  (а/a в/b е/e к/k м/m н/h о/o р/p с/c т/t у/y х/x і/i ј/j ѕ/s) → **I/l/1/і/І → «l», O/0/о/О → «o»** → без роздільників. «Аdmin» (кирилична А), «ADMIN», «Ad_min» — один нік; «Ben1», «Benl», «BenI» — теж, «Alex», «AIex», «Аlех» — теж.
  «Гравець …» (префікс прихованих ніків) резервується **за скелетом** — і з латинськими двійниками («Гpавець»).
- **Свідомо вужче, ніж запропонований `\p{L}\p{N}`:** (а) класи `[[:alpha:]]`/`[[:alnum:]]` у Postgres залежать від локалі БД, а на
  хмарному Supabase вона, за старим повідомленням CLI #825, `C.UTF-8` (не перевірено; у CI — en_US) — правило мало б різну поведінку в
  JS, CI й на бою; явні діапазони однакові всюди; (б) `\p{L}` пускає грецьку, діакритичну латиницю, CJK тощо з купою двійників —
  кожен потребував би таблиці згортки; ми свідомо обмежились латиницею (ASCII) і кирилицею. **Наслідок для користувачів: нік без
  діакритики й emoji («Räikkönen» не пройде)** — розширювати лише разом із таблицями згортки регістру без залежності від локалі.
  Регістр ASCII й кирилиці згортається явними таблицями (`translate`), не `lower()`; усі дозволені літери мають пару в таблиці.
  **Свідомий компроміс (рішення координатора 20.11):** законні близькі ніки — «Alex1» і «Alexl», «Boris» і «B0ris», «Ben1» і «Beni» —
  рахуються дублем і блокуються; це допустима ціна захисту від підміни (гравець додає символ). Нік «Beni»/«Benl» теж конфліктує через i→l.
- **У БД (міграція 0016, НЕ правка 0015):** `play.nick_valid(text)` і `play.nick_skeleton(text)` (IMMUTABLE), `profiles_nick_chk` тепер
  `check (play.nick_valid(nick))`, генерована колонка `nick_key = play.nick_skeleton(nick)` з **унікальним індексом
  `profiles_nick_key_idx`** (замість `profiles_nick_lower_idx`), `play.set_nick` нормалізує NFKC на боці бази (прямий виклик RPC з
  публічним ключем обходить сайт). Помилки: 23514 — формат, 23505 — зайнятий або надто схожий; тексти uk/en оновлено.
- **Паритет JS↔SQL:** `scripts/db/gen_nick_fixture.mjs` генерує `scripts/db/fixtures/nick_parity.json` (104 зразки: придатні, довжина,
  невидимі/RTL/zero-width, комбівні, emoji, інші письма, роздільники, зарезервоване, омоглифи) з `nick-rules.mjs`; **vitest**
  (`nick-rules.test.ts`) перевіряє, що JS дає ті самі відповіді, а **`test_play.py`** — що `play.nick_valid`/`play.nick_skeleton`
  дають ті самі на тих самих зразках. Додатково тести БД: підміни (Admin/Аdmin, Pavel/Рavel, роздільники+регістр, БОРИС/Борис,
  Сергій/Cергій), нормалізація NFKC в `set_nick`, відмови за emoji/діакритикою/грецькою/комбівним/подвійним пробілом; e2e: невидимий
  символ, emoji, регістр, кирилична Р → «зайнятий або надто схожий».
- **Не виміряно / відкрито:** (1) `normalize(..., NFKC)` і регулярка з `\uXXXX` у дужках — перевіряє `db.yml` на Postgres 17 (на бою
  версія Unicode у Postgres може відрізнятися від Node; зразки фікстури стабільні); (2) існуючих рядків у `play.profiles` немає (0015
  і 0016 застосовуються разом) — додавання генерованої колонки безпечне; (3) гомогліфи поза кирилицею/латиницею не потрібні, бо інших
  письм немає.

#### Фаза 9a — нік, остаточний круг (20.11): один скрипт + цифро/літеро-подібна кирилиця
- **Правило одного скрипту (UTS #39, «mixed-script»):** літери ніка — або лише латиниця, або лише кирилиця; цифри й роздільники — з будь-яким.
  Змішаний нік («Аdmin» з кириличною А, «MaxЗ», «Гpавець») відхиляється одразу з зрозумілим текстом (`nick.errors.mixed`, uk/en); у БД —
  умова в `play.nick_valid` (`not (p ~ '[A-Za-z]' and p ~ '[\u0400-\u045F\u0490\u0491]')`), тож прямий RPC її теж не обходить. Це
  прибирає основний клас підміни; лишається **повноскриптова** (весь нік кирилицею, що виглядає як латинський: «Мах3» ↔ «Max3»,
  «Рха» ↔ «Pxa») — її ловить скелет.
- **Скелет доповнено:** з→3, б→6, ч→4 (цифро-подібні; з великими — після згортки регістру), г→r, п→n (літеро-подібні) — окрім уже
  згорнутих а/a в/b е/e к/k м/m н/h о/o р/p с/c т/t у/y х/x і/i ј/j ѕ/s та I/l/1, O/0.
- **Перевірка решти дозволеної кирилиці (рішення, а не недогляд):** згорнуто — в, к, м, н, о, р, с, т, у, х, а, е, і, г, п, з, б, ч.
  **Свідомо НЕ двійники** (форма відрізняється від будь-якої латинської літери/цифри): д, л, ф, ы, э, ю, я, ж, ц, ш, щ, и, й, ь, ъ,
  ё, ї, є, ґ та решта U+0400–U+045F (тест `кирилиця, яку свідомо НЕ вважаємо двійником…`). Для ь/ъ — за вказівкою координатора не чіпали.
  Двійники між самими цифрами й латиницею (5/S, 8/B, 2/Z) **не** згортаємо — не просили; компроміс «Alex1» ≈ «Alexl» уже прийнято.
- **Честно про межі:** повністю виключити підміну неможливо — повний набір UTS #39 (`confusables.txt`) не підключали, а список двійників
  складено вручну для двох дозволених скриптів. **Запасний механізм — модерація ніків (задача 9e):** приховати нік (`nick_hidden` →
  «Гравець XXXX») і заблокувати акаунт без втрати результатів.
- **Тести:** фікстура паритету JS↔SQL — 126 зразків (мішані скрипти, цифро-двійники, Ӏ та інші поза діапазоном, I/l/1, O/0, зарезервоване);
  vitest `nick-rules.test.ts` і `test_play.py` (SPOOFS: Max3/Мах3, Max3/МахЗ, Max6/Махб, Max4/Махч, Pxa/Рха, Nah/Пан, Rex/Гех, Ben1/BenI…
  та MIXED — відмова за `profiles_nick_chk`); e2e: повна кирилиця → «зайнятий або надто схожий», кирилична Р + латиниця → «один алфавіт».

### Фаза 9c — правки за двома незалежними ревью (21.11: `/code-review high` + ревізія безпеки)
Безпекове ревью дефектів рівня high не знайшло (перевірені IDOR, CSRF/Origin, дедлайн у базі, витік чужих прогнозів до дедлайну, кешування).
Кожну знахідку спершу **відтворено** (падаючий тест), потім виправлено; у дужках — що саме червоніло до правки.
- **A. Сезон із двох джерел — відтворено** (`predictions-season.test.ts`: `expected 2026 to be 2027`). Етапи йшли з календаря, а `season`
  (`year` у GET/POST, штамп, запит результатів) — з `site_meta.current_season`; після Абу-Дабі, коли календар уже 2027, а `site_meta` ще 2026, сторінка
  показала б етапи 2027 з `year=2026` → 409/`unknown_round`. Тепер **сезон прогнозу = `page.season` календаря**; результати для «команди без фінішу» беруться
  із **останнього сезону, де вони є** (`site_meta`), і сезоном прогнозу не показуються. **Факт (read-only запит до прода, 21.11):** сезону 2027 у базі ще **немає** —
  `f1.rounds` / `season_rounds` для 2027 порожні, максимум у `calendar_sessions` — 2026, `site_meta` = {current_season: 2026, last_round: 20}. Гіпотеза
  «до грудня 2027 уже в базі» **не підтверджена**; сьогодні розбіжності на проді немає, помилка слідувала з коду (тест на моку). Обмеження: склад сітки
  (`team_index.current_drivers`) і команди — минулого сезону, поки не з'явилися результати нового; зміни складів 2027 між сезонами з'являться лише з даними.
- **B. 403 → «сесія закінчилась» — відтворено** (`predictions-rest.test.ts`: `403 {}: expected 'unauthorized' to equal 'unavailable'`; цей тест закріплював хибну
  поведінку). Тепер «не ввійшов» — лише 401 або код `28000`; 403 від PostgREST (42501: немає grant, схему `play` не відкрито) — **збій сервісу**.
- **C. Чужі прогнози: один `limit=200` на Q+R — відтворено** (замість двох запитів по виду йшов один; підпис «Показано перших 200» рахується по виду). Тепер **запит
  по виду** (`kind=eq.Q` / `kind=eq.R`, кожен зі своїм лімітом); якщо список виду заповнений до ліміту, а рядка гравця (за публічним іменем) у ньому немає,
  його рядок докладається окремим запитом (`player=eq.<ім'я>`, `limit=1`), тож гравець завжди бачить власний прогноз. Помилка одного з видів → `ok:false` (не
  показуємо половину таблиці). Сортування (очки ↓, нік) без змін.
- **D. Ввійшов, але збій бази → «Увійдіть» — відтворено** (route: немає `signedIn`; UI: картка входу в стані `user=null, unavailable`). Відповідь тепер має
  `signedIn`; `signedIn: true` + `user: null` + `unavailable` = «ввійшов, база недоступна». Картка входу показується лише при `!signedIn && !unavailable`
  (правило 9a: unknown ≠ «не ввійшов»); при збої — повідомлення «недоступно».
- **E. Збережений пілот/команда, яких немає на сітці, — відтворено** (форма: слот порожній у `<select>`, але id лишався в стані й ішов у POST). При
  ініціалізації невідомі id замінюються на «порожньо» з попередженням; знімок «збереженого» лишається вихідним, тож форма показує «є незбережені зміни».
  У режимі перегляду замість «?» — «Пілота/Команди вже немає на сітці».
- **F. 401 без переходу до входу — відтворено** (`onUnauthorized` не було). Тепер 401 → сторінка перечитує стан → картка входу з `?next=`.
- **G. Підсвітка «ви» — відтворено** (порівняння з `nick`, а вид віддає `public_name`; у прихованого — «Гравець XXXX»). GET повертає `user.publicName`; таблиця
  порівнює саме з ним (і саме його імʼя іде в запит «мого» рядка з C).
- **H. 403 origin → «Акаунт заблоковано» — відтворено** (`errorOf`). «Заблоковано» — лише при `error: "blocked"`; `no_profile` — окремо; будь-який інший 403 — «недоступно».
- **I. Закриття при відстаючих годинниках — відтворено** (`expected 2 to be 3`: лише один перечит). Тепер: негайний перечит, потім ще **два повтори (2 с, 5 с)**
  і зупинка; щойно сервер каже «закрито» — лічильник скидається. Перехід «відкрито → закрито» **переносить фокус** на блок стану (`section[aria-label]`,
  `tabindex=-1`); перший кадр, який уже закритий, фокус не краде.
- **J. A11y — зроблено:** обмін місцями оголошується в `aria-live` («Пілот X тепер на місці N. Місце M: Y»), `aria-required` на місцях 1–3, `aria-describedby` на
  блок помилки в невалідних слотах.
- **Тести:** +`predictions-season.test.ts`; розширено `predictions-rest.test.ts` (B, C: по виду, власний рядок, помилка одного виду) і `route.test.ts` (D, G); нові

## 2026-11-21 · Cloudflare Turnstile на формі входу (вхід кодом на пошту)
- **Навіщо:** `POST /api/auth/code` розсилає листи на довільні адреси. Мʼякий ліміт сайту (`limiter.ts`) — у пам'яті інстанса і не межа безпеки; справжні ліміти — у Supabase (пауза 60 с на адресу, листи на годину по проєкту). Бот міг би (а) засипати чужі скриньки листами з нашого домену, (б) вибрати годинний ліміт проєкту — і справжні гравці не отримували б кодів. Гіпотеза про сценарій, не відтворена; Turnstile закриває обидва без картинок-головоломок.
- **Токен перевіряє Supabase, не наш сервер.** Supabase Auth вміє CAPTCHA protection з Turnstile: секретний ключ лежить у Supabase, а наш `api/auth/code` лише передає токен у GoTrue `/otp` як `gotrue_meta_security.captcha_token`. У нас — тільки публічний ключ віджета `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (Vercel env, при збірці). Чому саме так: виклик `/otp` напряму (повз наш сервер, з публічним ключем проєкту) також іде в Supabase — якщо CAPTCHA ввімкнена лише в нашій формі, її обходять; ввімкнена в Supabase — вимагається від усіх.
- **Без ключа — як раніше.** Немає `NEXT_PUBLIC_TURNSTILE_SITE_KEY` → віджета нема, скрипт Cloudflare не вантажиться, токен не потрібен, CSP не змінюється, пункт у «Про сайт» схований. Тому код можна вливати до ключів.
- **З ключем:** сервер без токена → `400 captcha_required` (без виклику GoTrue і без витрати ліміту); GoTrue `captcha_failed` → `400 captcha`; UI: «Не вдалося пройти перевірку. Оновіть сторінку й спробуйте ще раз.» Тіло запиту до `/api/auth/code` дозволено до 4 КБ (токен до 2048 символів; ліміт 2 КБ його відсікав би).
- **Віджет** лише на формі входу, скрипт — динамічно після монтування (`render=explicit`), режим Managed, `appearance: interaction-only`, `size: compact` (320 px без прокрутки), тема auto, мова за локаллю. Токен одноразовий: після кожної відправки віджет скидається (на кроці коду — новий екземпляр), кнопки чекають токен («Перевірка…», live-регіон). Скрипт заблоковано / помилка віджета → спроба одразу дає помилку captcha без запиту.
- **CSP** (`buildCsp` у `next.config.ts`): `https://challenges.cloudflare.com` у `script-src`, `frame-src`, `connect-src` — лише коли ключ заданий при збірці.
- **Порядок вмикання (критичний):** (1) створити віджет у Cloudflare (Turnstile → Add widget, домен `outlap.org`, Managed), (2) `NEXT_PUBLIC_TURNSTILE_SITE_KEY` у Vercel (Production) + redeploy, (3) ЛИШЕ ПІСЛЯ цього — Supabase → Authentication → Attack Protection → Enable CAPTCHA protection → Turnstile → Secret key. Увімкнення в Supabase до деплою з ключем зламає вхід усім: сайт не присилатиме токен.
- **Не робили:** CAPTCHA на `verify` (код підібрати важко: ліміти 30/10 за 10 хв, див. `allowVerify`), на кнопці «Видалити акаунт»/нік (потрібна сесія). Серверної перевірки токена на нашому боці немає (secret у Supabase). Реальна мережа Cloudflare в тестах не використовується (скрипт підміняється `window.turnstile`).
