# Slipstream · Фаза 2 «Дані» — план реалізації

> **For agentic workers:** Implement this plan task-by-task, checking off each step; verify each task before moving on. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** історична база F1 у Supabase (схема `f1`), яка сама оновлюється після гонок, і з якої сайт бере дані: розділ «Команди» перемикається зі знімка на базу без жодної зміни на сторінці, а лічильники рахуються за правилами, перевіреними у фазі 3a.

**Architecture:** схема й завантажувачі переносяться з `f1-predictor/feat/f1-history-db` (міграція 004, `scripts/jolpica/*`) у цей репозиторій. Похідні числа (Гран-прі, перемоги, Кубки, роки, склад) рахує SQL — матеріалізовані подання, що оновлюються після кожного завантаження. Сайт лишається статичним: під час збірки читає подання через PostgREST Supabase (`fetch`, ключ anon, лише на сервері); після оновлення даних GitHub Actions викликає deploy hook Vercel — сторінки перезбираються. Наш власний контент (фото й автори, кольори, назви кирилицею, злиття команд) — у репозиторії (`src/data/curated/`), як рекомендовано в дорожній карті.

**Tech Stack:** Supabase Postgres (Free, проєкт `etalckupezpmworvfvgv`, лише схема `f1`), Python 3.12 + `psycopg` (завантажувачі), GitHub Actions (cron + Postgres service container для тестів), Next.js 16.4.5 (build-time `fetch`), Vitest.

**Spec:** дорожня карта фази 1 (`docs/plans/2026-11-10-phase1-foundation.md`, рядок «2. Дані»); правила лічильників і еталонні числа — `docs/audits/phase3a-data.md`, `src/lib/data/__tests__/teams-snapshot.test.ts`; контракт даних — `src/lib/data/types.ts`; джерело коду — `~/Desktop/F1/f1-predictor` гілка `feat/f1-history-db` (`supabase/migrations/004_f1_history.sql`, `scripts/jolpica/{load_dump,topup_api}.py`, `scripts/db-tests/`, `.github/workflows/f1-history-sync.yml`); рішення користувача 09.11 (лише схема `f1`, таблиці Predictor не чіпати) і 11.11 (повні перевірки — після готового результату; «Пілоти 2026» — склад останньої гонки).

## Global Constraints

- Global Constraints фаз 1 і 3a діють (версії, мови, CSP, бюджети Lighthouse — метод devtools, правила контенту).
- Supabase Free: БД ≤ 500 МБ на весь проєкт (разом із Predictor); Actions — 2 000 хв/міс; Vercel Hobby — без комерції.
- Запис у базу — лише роль postgres/service з GitHub Secret; сайт читає лише anon через RLS «public read» (є в міграції 004). Ключі — лише на сервері, не в клієнтському бандлі, не в репо.
- Python-залежності — точні версії в `scripts/requirements.txt`; перевірка постачання (PyPI: вік релізу, автор) перед додаванням. Нових npm-залежностей не додаємо (PostgREST — звичайним `fetch`).
- Правила лічильників (замір фази 3a): **перемоги — за гонками** (спільна машина 1950-х — одна перемога); **Гран-прі — гонки, де стартувала хоча б одна машина** (без DNQ/DNPQ/DNS/зняття за `detail`, і без записів grid 0 + 0 кіл); **Кубки — 1-ше місце в остаточному Кубку конструкторів з 1958**, поточного сезону — лише коли математично вирішено (відрив > максимум очок, що лишились); **злиття пар «шасі-двигун»** у родину (як `fam()` у `scripts/snapshot/teams.py`).
- «Пілоти {рік}» — склад останньої гонки (рішення користувача 11.11), порядок — за заліком пілотів.
- Робочий порядок (рішення користувача 11.11): у задачах — unit, lint, typecheck; повний пакет перевірок — Task 7.

## Review Focus

1. **Дані після свіжої гонки, але до нового дампу:** результати з API (`topup_api.py`) мають той самий вигляд для подань, що й з дампу — інакше числа стрибають щопонеділка. Тест у Task 3 (подання на базі «дамп + доливка» = еталон).
2. **Повторний або перерваний запуск синхронізації:** усе в одній транзакції, повтор не дублює рядки, перерване завантаження лишає старі дані — тест у Task 2.
3. **Супабейс недоступний під час збірки Vercel:** збірка має впасти з ясною помилкою, а не викласти сторінку з порожнім списком — тест у Task 4.
4. **Поточний сезон, титул ще не вирішено:** Кубок не зараховується передчасно — тест у Task 3 на сезоні в процесі.
5. **Розмір бази:** після повного завантаження (з колами) проєкт уміщується в 500 МБ разом із Predictor — замір у Task 5.
