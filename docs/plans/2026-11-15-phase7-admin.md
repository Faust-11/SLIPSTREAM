## Що вже є в репозиторії (заміри 15.11)
- Контент і ручні дані — файли: `content/stories/<slug>/{story.json,uk.md,en.md}` (33 історії), `src/data/curated/*.json`

  розмірах webp; автор і ліцензія — у JSON (`credit`). Готують їх Python-скрипти `scripts/curated/*` (Commons → webp).
- Наповнення: портрети 427 пілотів з ~790 (+91 відхилених кандидатів), фото боліда 127 команд зі 166, схеми 59 трас з 78.

  вкладемось у ліміт функції Vercel Hobby, бо беремо з Commons готовий ескіз ~1600 px, а не оригінал на 8000 px —
  перевірю замірами на 5 реальних файлах).

- CI: `check` (unit + e2e) ~7–8 хв, `lighthouse` ~16 хв на PR (PR #35); CI не запускається на чернетках PR.

## Архітектура (пропозиція)
1. **`/admin` у тому ж Next-застосунку**, лише українською, `noindex`, поза sitemap, той самий CSP. Сторінки — серверні,
   форми — server actions; для сторонніх — 404 (не «доступ заборонено»), щоб адмінку не було видно.
2. **Вхід через Google** (як у макеті й у фазі 9), список адмінів — на сервері (змінна середовища з e-mail). Сесія —
   httpOnly cookie. Технічний варіант (Supabase Auth чи Auth.js без бази) — у плані реалізації після замірів: Supabase
   спільний із Predictor, вмикання Google-провайдера там зачіпає і його.
3. **Публікація = PR у GitHub.** «Зберегти чернетку» → коміт у гілку `admin/<розділ>-<час>` + чернетка PR (CI не
   запускається — хвилини не витрачаються). «Опублікувати» → PR готовий → CI → злиття Rebase and merge → прод. Токен GitHub
   (fine-grained, лише цей репозиторій: contents + pull requests) — лише на сервері Vercel. Правило «у main — лише через
   PR із зеленим CI» зберігається.
4. **Попередній перегляд** — превʼю Vercel цього PR (посилання «Подивитись до публікації»).
5. **Журнал і відкат** — з історії git (коміти адмінки), «Відкотити» = PR зі зворотним комітом. Окремої таблиці не треба.
6. **Фото:** пошук на Commons (з правилами ліцензій макета) → вибір + точка фокусу → сервер нарізає webp (sharp) і кладе
   файли + `credit` у той самий PR. «Зняти за запитом автора» — PR, що прибирає фото й ставить заглушку.

## Що ще пригодиться (пропоную додати до макета)
1. **Контроль виходу на прод.** Сьогодні (15.11) злиття PR #35 загубилось на боці GitHub (502) — Vercel не зібрав прод, і це
   помітили лише вручну. Адмінка після кожної публікації звіряє, що прод отримав новий коміт, і якщо ні — кнопка «Викласти»
   (Deploy Hook Vercel, безкоштовно).
2. **Після гонки — один екран-чеклист:** результати підтягнулись, хайлайт гонки знайдено (зараз — ручний перезапуск
   `race_videos.py`), у нових пілотів/команд є фото, у сезону — фото чемпіона/переможця.
3. **Здоров'я джерел історій:** щотижнева перевірка мертвих посилань + кнопка «Зберегти в Web Archive» (у макеті є лише
   лічильник «без архіву»).
4. **Ліміти безкоштовних тарифів:** хвилини GitHub Actions (з 1.12, після закриття репо, — 2 000 хв/міс; квоту вже
   вичерпували 14.11), розмір бази Supabase (103,9 МБ з 500 МБ, замір 14.11), Vercel.
5. **«Знайшли помилку?»** — кнопка на сторінках для відвідувачів, звернення падають у чергу адмінки. Потрібне сховище (база)
   і захист від спаму — можна відкласти до фази 8/9.
6. **Економія хвилин CI для правок контенту:** PR з `admin/*`, що змінюють лише `content/**` чи `src/data/curated/**`,
   ганяють легкий набір (unit + перевірка історій + збірка + e2e лише зачеплених сторінок), без повного e2e і Lighthouse.

Прибираю з макета: «Резервна копія бази» для контенту (контент тепер у git; база відновлюється з Jolpica). Резервні копії
знадобляться у фазі 9 (рекорди гравців у базі).

## Технічні рішення 7a (заміри 15.11)
- **Вхід:** Google OpenID Connect напряму (бібліотека `oauth4webapi` — PKCE, state, nonce, перевірка ID-токена), сесія —
  підписаний JWT у httpOnly cookie (`jose`, HS256, 12 год, `Secure`, `SameSite=Lax`, `Path=/admin`). Supabase Auth не
  беремо: у міграціях SLIPSTREAM `auth.*` не використовується, проєкт Supabase спільний із Predictor — вмикання
  Google-провайдера зачепило б і його. Бази для входу не треба. Обидві залежності — перевірити supply-chain перед додаванням.
- **Список адмінів** — `ADMIN_EMAILS` на сервері; ID-токен Google має `email_verified = true`.
- **Сторонній** (не увійшов або не в списку) на будь-якій `/admin/**` і server action — 404.
- **Публікація:** GitHub Git Data API (blobs/trees/commits — і для бінарних фото) → гілка `admin/<розділ>-<час>` → PR
  (чернетка = draft PR без CI) → «Опублікувати» = ready → CI → workflow `admin-merge.yml` (`workflow_run` після CI,
  перевіряє префікс гілки й перелік змінених шляхів) → Rebase and merge.
- **Контроль проду:** для злитого коміту чекаємо статус `Vercel = success` на main; немає за 15 хв → «Потребує уваги» +
  кнопка «Викласти» (Vercel Deploy Hook, URL лише на сервері).
- **Журнал і відкат:** злиті PR з міткою `admin` (GitHub API); «Відкотити» = новий PR, що повертає файли до стану перед
  злиттям.
- **Тестування без справжніх ключів:** фейковий OIDC-провайдер і фейковий GitHub API на localhost у e2e (як
  `scripts/dev/fake-postgrest.mjs`); справжні ключі — лише в змінних Vercel.
- **Що знадобиться від користувача** (наприкінці 7a, перед перевіркою на превʼю): клієнт OAuth у Google Cloud Console,
  fine-grained токен GitHub (лише цей репозиторій: contents + pull requests), Deploy Hook у Vercel, змінні середовища у
  Vercel. Я дам покрокову інструкцію; ключі вводить користувач.
